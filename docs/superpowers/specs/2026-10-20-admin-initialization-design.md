# 管理员首次初始化与现有数据实例设定

## 目标

- 新服务器首次部署时，未初始化的实例显示“设置管理员”页面，由部署者自行设置管理员账号和密码。
- 当前已有业务数据、但尚未初始化管理员的实例，设置账号 `admin`，密码使用用户本次提供的值。
- 管理员初始化不得删除、重建或改写现有账号及其他业务数据。

## 现状

项目已经实现首次初始化流程：`GET /api/auth/status` 返回初始化状态；未初始化时前端显示设置页面；`POST /api/auth/setup` 校验服务器数据目录中的一次性设置码，保存加盐 scrypt 密码哈希，并使设置码失效。

当前 `data/accounts.sqlite` 中管理员用户名为空、一次性设置码有效，同时包含 102 条账号记录。因此不需要新增或修改前端、接口或数据库结构。

## 实施方式

通过现有 `POST /api/auth/setup` 初始化当前实例。请求使用：

- 管理员账号：`admin`
- 管理员密码：使用用户本次提供的值，仅在初始化请求的进程内存中处理
- 当前 `data/admin-setup-code.txt` 中的一次性设置码

不直接修改 SQLite，避免绕过密码哈希、并发版本检查、登录限流和设置码失效逻辑。明文密码不写入源代码、配置文件、文档或日志，也不作为命令行参数传递。

## 数据与安全行为

- 密码符合现有 12–128 字符规则。
- 服务端仅保存随机盐与 scrypt 派生哈希，不保存可还原明文。
- 初始化成功后删除一次性设置码文件并清空其数据库摘要。
- 初始化产生的临时会话不作为后续验证凭据；验证通过重新登录完成。
- 账号记录、组织信息、PAT、WorkBuddy 配置和 API Key 均不改变。

## 验证

1. 初始化前记录业务账号总数为 102，管理员状态为未初始化。
2. 执行现有初始化接口，确认返回 HTTP 201 且状态为已认证。
3. 确认管理员状态已初始化、用户名为 `admin`，一次性设置码文件已删除。
4. 使用管理员账号和本次提供的密码重新登录并确认成功，验证过程不输出密码。
5. 再次统计业务账号，确认仍为 102。
6. 运行管理员认证相关自动化测试；若未修改源代码，测试用于回归确认现有初始化流程。

## 回退

若初始化失败，保持数据库原状并报告具体错误。若初始化成功后需要重设，停止服务后运行 `npm run admin:reset`；该操作仅重置管理员登录信息并生成新的一次性设置码，不删除业务数据。
