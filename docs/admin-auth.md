# 后台登录与服务器部署

后台现在强制管理员登录，本机访问也不例外。对外 API 使用独立 API Key，不能用 API Key 登录后台，后台 Cookie 也不能代替 API Key。

## 首次设置管理员

1. 启动项目后打开工作台。未设置管理员时显示「设置管理员」。
2. 在**服务器的数据目录**找到 `admin-setup-code.txt`（默认 `data/admin-setup-code.txt`），读取里面的一次性设置码。代码不会在网页或接口中公开。
3. 填写设置码、管理员账号和密码。账号为 3–40 位字母、数字或 `_ . @ -`；密码为 12–128 个字符。
4. 设置成功后自动登录，设置码立即失效，文件会被删除。没有默认管理员密码，也不能通过公开网页跳过设置码。

自定义 `ACCOUNT_DESK_DATA_DIR` 时，设置码在该目录下。Linux 文件权限为仅文件所有者可读写；Windows 需确保数据目录继承合适的用户访问权限。不要把数据目录放到网站静态目录。

## 日常操作

- 顶栏显示管理员账号，钥匙按钮「修改登录密码」，退出按钮「退出登录」。
- 登录会话绝对有效期 12 小时，另有 2 小时空闲超时（只有真正发请求才续期）。最多同时保留 8 个会话（超出时自动清理最久未活动的）。
- `GET /api/auth/sessions` 列出活动会话（创建时间、最后活动时间、是否为当前会话，只显示摘要前 12 位）；`DELETE /api/auth/sessions` 撤销除当前会话外的全部会话，怀疑 Cookie 泄露时先做这一步。
- 密码修改需要当前密码。成功后其他所有旧会话失效，当前窗口获得新会话。
- 退出会删除服务器端会话；账号列表等页面在登录失效后关闭并返回登录页。
- 会话使用 HttpOnly、SameSite=Strict Cookie；HTTPS 域名使用 Secure 与 `__Host-` Cookie 前缀。浏览器 localStorage/sessionStorage 不保存密码或会话密钥。
- 密码使用随机盐与 scrypt 哈希，服务器不保存可还原的管理员密码。初始化/登录/修改密码总计每分钟最多 60 次尝试，最多 2 个并行密码计算；计数跨重启保留。
- 连续失败第 5 次起叠加递增冷却：30 秒、60 秒、2 分钟、4 分钟、8 分钟，上限 15 分钟；等待期内正确密码同样返回 429。成功登录后计数清零。
- 冷却**按来源分桶**，一个来源被锁不影响其他来源。本机回环地址共用一个桶；反向代理后用 `ACCOUNT_DESK_TRUST_PROXY=1` 按真实客户端区分来源。被锁在自己机器外面时执行 `npm run admin:unlock`（或在另一个已登录窗口点「解除锁定」）即可立即恢复，不必等冷却结束。
- 用户名错了也完整跑一次 scrypt 再比较，避免用响应时间判断管理员账号是否存在。
- 初始化、登录成功/失败/锁定、解除锁定、改密、撤销会话、自动清理旧会话、身份再验证失败、读取凭据、导出明文、TOTP 启用/关闭/失败、恢复码使用、被拒的 Host 与 Origin 都记入 `security_events`（保留最新 5000 条，不含任何密码或令牌）。`GET /api/auth/events?limit=100` 读取。
- 哈希参数带版本号记录在 `admin_credentials.hashVersion`：当前为 v2（N=2^17, r=8, p=1），旧库的 v1（N=2^14）记录在下次登录成功时自动重算为 v2，无需重置密码；单次登录约多耗 0.5 秒。
- 私有接口写操作同时校验会话与 CSRF token，并在接收完整请求体后再次校验，上传途中退出的请求不会继续提交。
- 不记录密码、设置码或请求正文。

## 读取明文凭据的二次验证

查看账号密码、TOTP 密钥或导出 TXT 时，除了会话还需要一次**身份再确认**：

1. 前端弹出「确认身份」，要求重新输入登录密码（启用两步验证时还要动态码）。
2. `POST /api/auth/reauth` 返回一个 5 分钟有效、最多可用 5 次的令牌，前端放在 `X-Reauth-Token` 请求头里。
3. 令牌**绑定签发它的会话**，换浏览器或换会话都不认；过期或用满次数后重新输入密码，界面会自动重新弹窗。
4. 每次成功读取都会写入：`credential_access` 表（时间、动作、具体账号、条数、会话摘要前 12 位，保留 2000 条）与 `security_events`（安全中心可见）。导出会把涉及的账号标识记进这一行，不只是条数。
5. 被拒绝的读取不写审计、也不消耗次数，避免把失败尝试误记成"读过"。

## 可选的两步验证（TOTP）

在左侧导航「安全中心」→ 顶部「两步验证」卡片 →「立即启用」中启用：

- 生成 160 位随机密钥（加密存储），用验证器 App 手动输入该密钥。
- **必须输入一个当前能通过的动态码才会真正启用**，半途退出不会锁死自己。
- 启用后一次性给出 8 个恢复码，只显示一次，每个只能用一次。
- 关闭需要登录密码 + 当前动态码或恢复码。
- 忘记验证器且恢复码用完：停服务后执行 `npm run admin:reset`，会清空 TOTP、恢复码与登录凭据，重新生成一次性设置码；账号库与 API 密钥不受影响。

## 忘记密码 / 丢失设置码

需要服务器文件及命令行权限：

```bash
# 先停止项目服务，然后在项目目录执行
npm run admin:reset
```

若原来使用自定义数据目录，执行时使用相同的 `ACCOUNT_DESK_DATA_DIR`。重置命令会检查运行锁；服务仍在运行时拒绝操作。

该命令撤销后台登录会话并生成新的 `admin-setup-code.txt`，保留账号、分组、标签、PAT、WorkBuddy 配置与 API 密钥。重新启动后，用新设置码重新设置管理员。

## 同一个域名部署后台与 API

例如 `www.abc.com`：

| 浏览器 / 程序请求 | 反向代理目标 |
| --- | --- |
| `https://www.abc.com/` 与 `/api/auth/*`、其他后台接口 | `127.0.0.1:4318`，后台登录鉴权 |
| `https://www.abc.com/api/v1/*` | `127.0.0.1:4319`，独立 API Key 鉴权 |

不需要额外注册 API 子域名。在运行项目的进程环境中设置：

```bash
ACCOUNT_DESK_ADMIN_ORIGIN=https://www.abc.com
ACCOUNT_DESK_API_ORIGIN=https://www.abc.com
# 可选：TLS 在代理上终止、且希望按真实客户端区分登录锁定来源时开启
# ACCOUNT_DESK_TRUST_PROXY=1
```

这两个值只包含 origin，不带路径或末尾 `/api/v1`。只支持 HTTPS 公网 origin，本机回环访问允许 HTTP。设置后重启项目。

使用项目 `deploy/Caddyfile.full` 模板，将域名替换为实际域名。Caddy 自动配置 HTTPS，并保留原始 Host。不要把代理 Host 强制改成 `127.0.0.1`，否则 Cookie 安全标记及来源校验无法按公开 HTTPS 域名正常工作。

服务器防火墙只开放需要的 SSH 与 80/443；4318/4319 保持不对公网开放，两服务仍只监听回环。首次管理员设置必须由持有服务器设置码的人完成。

### 用 nginx 加一层 IP 白名单

`deploy/nginx.conf.example` 是一份可直接改用的 nginx 配置：后台整站要求白名单（`allow` 若干条后跟 `deny all`），`/api/v1/*` 仍转到 4319 供外部程序调用。三个容易踩的点：

- `Host` 必须原样透传（`proxy_set_header Host $host`）。改写成 `127.0.0.1` 会让应用的来源校验把请求判成跨站并 403。
- `X-Forwarded-For` 要用 `$remote_addr` **覆盖**，不要 `$proxy_add_x_forwarded_for` 追加。默认不信任该头，只有设了 `ACCOUNT_DESK_TRUST_PROXY=1` 才采信；用追加写法会让客户端自己伪造来源，绕开按来源的登录锁定。
- 白名单只做在代理层时，应用自己不知道谁被挡住了，也不会写 `security_events`。想看到"谁被拒绝"的审计记录，需要在代理层日志里查。

### 应用层的来源白名单

如果不想维护两份规则，可以只保留应用层：`安全中心 → 访问白名单` 里填地址（支持 CIDR 与 IPv6），或者用 `ACCOUNT_DESK_ADMIN_ALLOW=1.2.3.4,10.0.0.0/8` 播种首次配置。越界来源返回 403 并写一条 `ip_rejected`，可在安全事件里看到，也会按「异常与渗透迹象」推送。

- 本机回环始终放行，所以规则写错时仍能从服务器上登录改回来。
- 代理层的 `allow` / `deny` 仍然值得保留：它在 TLS 握手前就挡住流量，代价更小。两层不冲突，应用层是兜底。
- 带代理时同样需要 `ACCOUNT_DESK_TRUST_PROXY=1`，否则应用看到的来源永远是 `127.0.0.1`，白名单会变成"只允许本机"。

若后台与 API 使用不同域名，分别设置两个 origin；为后台域名全部代理到 4318，为 API 域名使用 `deploy/Caddyfile.api` 代理到 4319。

本机 / SSH 访问 `http://127.0.0.1:4318` 仍然需要登录；此入口使用适合本机 HTTP 的独立 Cookie，**默认完全不信任**客户端发来的 `X-Forwarded-Host`、`X-Forwarded-Proto`。只有显式设置 `ACCOUNT_DESK_TRUST_PROXY=1` 时，才会采信代理链中最靠近服务端的一跳：用它区分登录锁定的来源，并在 `X-Forwarded-Proto: https` 时下发 `Secure` + `__Host-` Cookie。私有工作台的 Host 和 Origin 必须与已配置地址一致。

## 验证边界

- 未登录打开域名：看到初始化或登录页，不显示账号数据。
- 未登录请求 `/api/accounts` 并带 `X-Local-Client: account-desk`：401。
- 仅带 API Key 请求 `/api/accounts`：不能读取后台数据。
- 请求 `/api/v1/groups` 不带 API Key：401；带具备读取权限的 Key：200。
- 登出后旧 Cookie 不再有效；修改密码后其他旧会话不再有效。
- 浏览器内置 API 调用文档仍在「API 管理」页面；原来的「使用说明」独立页面和菜单已删除。

真实服务器的域名解析、TLS、反向代理和防火墙需在部署时验证。本项目的本地验证不等于已部署公网服务。
