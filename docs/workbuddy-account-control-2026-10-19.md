## 分叉点和原因边界

两条链路都到达 WorkBuddy GitHub 回调接口。服务端在该回调的 302 Location 中选择不同的关联路径：已有身份继续登录，首次关联身份进入准入处理并返回 403。因此，可以将当前失败定位在首次身份关联阶段；不是 GitHub 密码/2FA 页面卡住，也不是授权按钮没点击。

已有账号在相同项目浏览器配置下可登录，否定了“项目浏览器或当前网络对所有账号都完全不可用”的说法。但没有测量每条请求的公网出口 IP，只有代理配置相同；不能排除代理按目的地/时间分流，也不能排除网络、客户端和账号属性共同参与首次关联风控。

风控上下文接口 code=0 仅证明提交成功，不能解释为安全评分通过。服务器没有返回具体风控子码；本轮仍不能证实是账号年龄阈值、注册批次、地区、IP 信誉、首次关联资格还是其他规则。没有尝试改写风险信号、伪造参数或绕过服务端拒绝。

## 同时定位到的项目漏判

成功样本实际进入官网并通过账号接口，但 OAuthSession 最后仍返回 `github_identity_missing`：`callback=true`、`identity=false`。

当前代码只在 GitHub 授权页面读取用户名，且只有在此页面读到预期用户名才设置身份凭据（`server/oauth-browser.js` 的 GitHub identity 分支）。本轮已授权账号的跳转没有给程序留下可用的用户名证据。已有页面结果与本地证据门槛不同，导致本地不能确认成功。

这是“远端已认证而本地没记成功”的独立问题，不是首次关联 403 的原因。修复必须补充与本次会话绑定的可靠 GitHub 身份证据，不能直接删除身份校验、用提交的用户名推定登录身份或凭昵称关联 UID。本轮仅诊断，未放宽生产代码验证条件。
