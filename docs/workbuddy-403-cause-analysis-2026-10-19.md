## 已查明与未查明

已查明：`first-broker-login` 是首次建立外部身份关联的流程入口；进入该路径与随后返回 403 是两个不同事件。当前抓包显示 WorkBuddy 在首次关联流程中明确拒绝，但没有暴露具体命中条件。

未查明：拒绝究竟由共享出口信誉/累计频次、设备关联、账号属性、首次关联规则或其他条件触发。手动登录失败、老账号能登录、风控上下文提交成功，都不足以单独排除 IP 或设备因素。

## 为什么失败样本走 first-broker-login

已读取 Keycloak 上游公开实现，`IdentityBrokerService.authenticated` 的主要分支是：

1. 用身份提供方及其用户 ID 查询已有外部身份关联。
2. 找不到已关联用户时，保存本次外部身份上下文，并重定向到 `first-broker-login`，执行首次用户创建/关联流程。
3. 找到已关联用户时，校验已有用户，再根据配置继续 `post-broker-login` 或完成认证。
4. 首次流程成功后也可以执行后置流程；`post-broker-login` 并非只能供老用户使用。

来源：[Keycloak IdentityBrokerService.java](https://github.com/keycloak/keycloak/blob/main/services/src/main/java/org/keycloak/services/resources/IdentityBrokerService.java)，本次保存副本 `output/workbuddy-keycloak-IdentityBrokerService.java`，关键位置为第 757、777、834、842、854、1003 行附近。

这是与 WorkBuddy URL、realm 和重定向形态相对应的标准框架机制。未取得 WorkBuddy 的服务端实现或版本，不能将上游实现当成其自定义风控规则源码。

已有 WorkBuddy 身份样本的回调直接重定向到后置流程，首次关联失败样本的回调重定向到首次流程，与上述机制一致。**不能倒因为果，声称因为账号被判风险所以才进入 first-broker-login。** 更准确的解释是：当前身份需要首次关联，因此执行这一路径；流程随后返回了安全拒绝。

## 浏览器登录过多：区分本地状态与服务端统计

当前实现为每个账号启动项目 Chromium，并创建独立的 `newContext`。每个账号结束后关闭会话，再继续队列，未使用持续累积账号 Cookie 的共享 profile。

因此，“一份浏览器 Cookie 登录过多导致串号/污染”没有得到现有实现和抓包支持。

但独立上下文不等于不同的设备或网络来源。服务端可以跨上下文关联公网 IP、浏览器/设备信号及登录频次；这类累计仍是未排除的候选原因。也不能通过 `navigator.webdriver=true` 一项就认定拒绝由自动化检测触发。

数据库只有一条浏览器清理异常记录，时间为 14:43:22，晚于首个已保存的 403。检查时没有发现本项目 Chromium 遗留进程；这些观察不支持用该清理异常解释 12:32 的拒绝，也不能还原全部历史进程状态。
